# Gates: F2.4 clean-install package contract across five artifact targets and all public entry points

Scope: F2.4 owns `npm/test/bamti-api.test.mjs` and package metadata under `npm/artifacts/`. It proves the published package archives as a consumer receives them; it does not substitute repository modules, fake executables, or host-built fallback payloads.

## Consumer proof

The test requires exactly these five real CLI archives in `BAMTI_STAGED_ARTIFACTS` (default `npm/dist/`):

- `bamti-cli-linux-x64-0.2.0.tgz`
- `bamti-cli-linux-arm64-0.2.0.tgz`
- `bamti-cli-darwin-x64-0.2.0.tgz`
- `bamti-cli-darwin-arm64-0.2.0.tgz`
- `bamti-cli-win32-x64-0.2.0.tgz`

The separate five `@bamti/bamti-*` native-addon packages are not F2.4 CLI artifacts and are not enumerated by this gate. Each CLI archive is installed with npm into a fresh root created under the operating-system temporary directory, outside the repository. npm runs offline with scripts disabled and a root-local cache. `NODE_PATH` is empty, and an import probe must prove that `bamti` cannot resolve before installation. The test checks canonical package name and version, exact OS/CPU selectors, the exact Rust target and payload path, absence of a competing platform-package `bin` entry, non-empty target binary, and executable mode where applicable. A normal install must accept only the host-matching artifact; forced installs are used only to inspect the other four archives and to prove that the API cannot mistake a wrong-platform package for the absent host package.

The test packs `npm/bamti` and `npm/bamti-cli` into real tarballs, installs those tarballs together with the real host artifact, and checks the installed `bamti` manifest has exactly these thirteen public exports:

1. `.`
2. `./package.json`
3. `./unstable/sync`
4. `./unstable/async`
5. `./unstable/fs`
6. `./unstable/proto`
7. `./unstable/ast`
8. `./unstable/ast/is`
9. `./unstable/ast/factory`
10. `./unstable/ast/utils`
11. `./unstable/ast/scanner`
12. `./unstable/ast/visitor`
13. `./unstable/ast/clone`

Every entry is imported from the installed package. The root API must locate the installed host CLI binary and execute its real `--version` operation successfully. The installed `bamti-cli` facade must own exactly `bin: { "bamts": "bin/bamts.js" }`; that entry must independently execute the same real binary and print a `bamts <version>` line. Separate consumers must reject a missing host artifact and a present wrong-platform artifact.

Targeted command:

```sh
node --test npm/test/bamti-api.test.mjs
```

Artifact prerequisite commands available in source build one target at a time:

```sh
node npm/scripts/package-platform.mjs --target x86_64-unknown-linux-gnu
node npm/scripts/package-platform.mjs --target aarch64-unknown-linux-gnu
node npm/scripts/package-platform.mjs --target x86_64-apple-darwin
node npm/scripts/package-platform.mjs --target aarch64-apple-darwin
node npm/scripts/package-platform.mjs --target x86_64-pc-windows-msvc
```

Current evidence: `node --check npm/test/bamti-api.test.mjs` passed. A narrow Node metadata check validated all five CLI templates at version `0.2.0`, including package names, OS/CPU selectors, Rust targets, payload paths, lack of platform-package `bin` entries, and the facade's exact `bamts` bin. `node --test npm/test/bamti-api.test.mjs` ran seven tests with zero skips and failed all seven only because the five real archives are absent. The exact first blocker is `npm/dist/bamti-cli-linux-x64-0.2.0.tgz`; the other four missing paths are the four remaining archives listed above. No binary payloads exist under `npm/artifacts/cli-*/bin/`. The test did not generate, copy, fake, or skip any archive or binary.
